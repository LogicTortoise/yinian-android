# 一念 Android V2 开发计划

## 目标

在 V1 的本地 Idea、Task、手动计划与专注数据上，完成产品方案阶段 C「个人规划」：时间规则、容量估计、重复事项、日历忙碌时间、确定性排期草案，以及专注回顾。V2 继续本地优先，不让模型直接改写计划。

V1 基线：公开仓库 `LogicTortoise/yinian-android` 的 `main` 初始提交 `681b6e5`。V1 自动化基线见 [`test-report-v1.md`](test-report-v1.md)。

## 范围和用户控制

- 支持按星期设置可用工作时间、休息间隔、缓冲和每日计划上限，并展示周容量估算。
- 支持日、工作日、每周等重复规则，生成稳定、可去重的任务实例；用户能修改单次实例或重复规则。
- 生成可解释的排期草案：检查依赖、工作时间、固定安排、重复事项、日历忙碌时间、专注时长和缓冲；列出未安排项及原因。
- 用户预览、编辑后再应用排期草案。新建的块默认是可移动的；已有固定块和用户正在做的任务受到保护。重复应用同一草案不生成重复块。
- 可选只读 Android 日历接入，将授权范围内的外部事件作为忙碌时间；V2 不向日历写入，不授予权限也能完整使用本地计划。
- 专注回顾以实际 FocusSession 和完成状态为数据，汇总每日/每周计划与实际投入；不读取应用使用情况，不给用户贴分心标签。

## 不包含

云端 LLM/ASR、账号同步、API/MCP、外部日历写入、可靠后台提醒、应用使用情况采集、复杂求解器和商店发布。排期使用确定性的本地规则，未配置服务不显示为已接通。

## 核心验收标准

1. V1 数据从数据库 v2 升级后不丢失。迁移过程有 instrumented 测试覆盖真实 Room schema；禁止通过 destructive migration 掩盖问题。
2. 相同输入和相同时间规则下，排期引擎产生相同结果。结果无互相重叠的块，不与固定/忙碌区间冲突，不安排依赖未完成的任务。
3. 排期可行时显示具体时段和原因；不可行时展示剩余容量、冲突或超限原因。算法不静默移动现有固定块或正在执行任务。
4. 预览不会写入计划；只有用户应用后才保存。重复应用同一草案幂等，冲突校验失败时保持原计划完整。
5. 重复事项覆盖规则生成、实例去重、单次修改和未来规则变更；时区/DST 与日期边界有测试。
6. 日历集成只读且可选，用户拒绝权限后其余规划能力照常工作；事件标题/详情不写入任务或日志。
7. 专注回顾只统计 FocusSession 的有效时段，不采集设备使用情况；暂停/恢复、跨午夜和取消会话按产品规则计算。
8. API 26+ 可安装；V1 的 JVM 与 instrumented suites 和 V2 新增 suites 全部通过，无 `@Ignore`、失败或跳过。

## 执行约定

- Claude Code 开发子代理负责 V2 生产实现与必要构建；Claude Code 测试子代理负责新增/调整测试并实际执行。两个子代理不并行写同一目录：先开发，再测试；发现生产缺陷后交回单独开发子代理修复，再由测试子代理回归。
- 控制器负责计划、边界审查、证据综合、提交和推送。
- 优先用现有 Compose、Room、DataStore、Coroutines 和 Java Time，不为本地排期引入云服务或大型约束求解依赖。
- 任何数据库迁移、日历权限和排期应用变更必须在报告中说明真实设备/模拟器、执行命令和实际通过数。
